## Подготовленные исправления

| Область | Ошибка | Новое поведение |
|---|---|---|
| Нормализация | Offline и online по-разному обрабатывали `_`, дефисы и `*`. | Один модуль задаёт общие правила текста и wildcard. |
| Wildcard | Терялся начальный wildcard. Offline не принимал пустое значение. | Сохранён начальный wildcard. Допускается ноль токенов. Шаблон без статического текста отклоняется. |
| C# | Имя `WriteLine` сравнивалось со строкой в нижнем регистре. | `Console.WriteLine` распознаётся. Для cartservice получены 14 шаблонов вместо 0. |
| Владение логом | Путь через DDG мог выбрать чужой метод. | Владелец определяется по `AST` и `CONTAINS`. |
| Точные кандидаты | Пустой результат Trie включал неточное сопоставление. | Пустой набор остаётся несовпадением. Только отсутствие Trie допускает прежний lexical API. |
| Корреляция | Логи разных запросов могли продолжить одну цепочку. | `--correlation-column` разделяет цепочки по заданному ключу. Отсутствующий ключ даёт необъяснённое событие. |
| Табличный вход | Пустая CALL-ячейка при корреляции считалась явно заданным ID. | Пустые ячейки преобразуются в отсутствие ID на границе CSV/DataFrame. Прямой API остаётся строгим. |
| Неполный граф | `INCOMPLETE_SEGMENT` мог стать успешным завершением. | Отчёт имеет `status=incomplete` и `termination_reason=incomplete_static_graph`. Старые JSON также поддержаны. |
| Финализация | Timeout и pruning могли удалить гипотезу из итогового отчёта. | `--emit-incomplete` сохраняет конечные active/incomplete/expired/pruned гипотезы и причины. |
| Условия FLOW | Условие одного метода удаляло ветви другого. | Условия ограничены своим методом. Они помечены как статические кандидаты. |
| Построение методов | Для каждого метода выполнялись два полных обхода CPG edges. | Читаются только исходящие рёбра AST-узлов метода. Порядок сохранён. |
| Coverage | Меньший граф мог выглядеть как улучшение. | Проверяются также reachable, log points, entrypoints и отсутствующие сервисы. |
| Метрики RCA | Отсутствующие ответы исключались из оценки. | Ground truth задаёт весь набор случаев. Пропущенный ответ получает пустой ranking. |
| CLI builder | Ошибка одного сервиса могла оставить exit code 0. | Успешные результаты сохраняются, но общий код становится ненулевым. |
| Ограничение benchmark | Потомок мог остаться после выхода родителя при timeout. | После периода завершения SIGKILL получает вся группа процессов. |

В отчёты гипотез добавлены ограничения доказательств. Накопленный score
не объявляется вероятностью. Совместимый статический путь не объявляется
наблюдённым исполнением. Последний лог перед возможным return не доказывает
фактический возврат. Ни один такой отчёт сам по себе не является диагнозом RCA.

В чистом Python-окружении прошли 157 тестов и 50 дополнительных subtests.
Среда и проверенная ревизия сохранены в [validation.json][validation].
Новые исправления получали тесты, которые падали до изменения.
Тот же набор повторно прошёл на версиях data libraries из `requirements.txt`:
pandas 3.1.1, NumPy 2.4.6 и Matplotlib 3.10.9. Основная измеренная среда
использовала pandas 2.2.3. В CI подготовлены оба варианта.

Использованы Joern `v4.0.689`, JDK 21.0.13 и Python 3.12.14.
JVM имела heap 3 GiB и `ActiveProcessorCount=2`. Последний параметр не задаёт

Пакет `server/src/main/java/org/opensearch/snapshots` содержит 30 Java-файлов.
Из 519 679 байт исходного текста получено 45 756 узлов и 333 948 рёбер.

### Второй источник задержки

После замены reader 175 секунд уходили на FLOW/FSM. Два метода
`MethodConstructor` каждый раз обходили все рёбра. Исправление сохраняет
порядок узлов и рёбер, но ограничивает обход узлами текущего метода.

| Метрика | До локального обхода | После |
|---|---:|---:|
| FLOW/FSM, с | 175,052 | 4,133 |
| Внутреннее время Python pipeline, с | 180,121 | 13,132 |
| RSS во время FLOW/FSM, MiB | 313,41 | 315,81 |
| Успешные точки входа | 89/89 | 89/89 |

Это сравнение по одному запуску. Baseline имел незаданный hash seed,
исправленный запуск — `PYTHONHASHSEED=0`. Хост был общим. В новом запуске
сама загрузка заняла 8,617 секунды. Поэтому главный вывод относится к
изменённому этапу FLOW/FSM. Числа графа, шаблонов и coverage совпали.

Точное равенство проверено отдельно в одном процессе. Полный `MethodGraph`,
сериализованные FLOW и FSM совпали для 254 точек входа bundled-сервисов
и трёх выбранных точек входа OpenSearch. Это 807 и 76 сборок методов.
Для этих проверок сохранён порядок списков. Побайтовое равенство двух полных
каталогов OpenSearch с разным hash seed не заявляется.
Подробности: [method-performance.md](method-performance.md).

После объединения всех исправлений выполнен ещё один запуск в чистом
окружении. На том же DOT он завершил 89/89 точек входа. Полная команда
заняла 10,319 секунды, включая запуск Python. Внутреннее время pipeline —
9,197 секунды. Время отдельных стадий: загрузка 5,699, шаблоны 0,111,
FLOW/FSM 3,188 и coverage 0,047 секунды.
Пик RSS команды составил 335,52 MiB. Coverage совпал с предыдущими запусками.
Это проверка итоговой версии, а не повтор изолированного сравнения двух
вариантов MethodConstructor. [Измерение полной команды][final-command] и

### Полный проект

Отдельный запуск выбрал все 13 770 отслеживаемых Java-файлов, включая tests,
plugins и libraries. Объём исходного текста — 124 664 521 байт.
Frontend остановлен по времени через 600,034 секунды. Пик RSS — 3 553,75 MiB.
Лимит RSS 4 GiB не сработал. CPG к моменту остановки отсутствовал.
Этапы overlays, export и Python для этого запуска не выполнялись.

CPU этого запуска не удалось измерить корректно. Исходный monitor получил
только CPU shell после остановки JVM. В результате записан `null`.
Monitor исправлен: для прерванных запусков он считает выборочную нижнюю
оценку CPU дерева процессов и явно помечает этот тип измерения.

OpenSearch не компилировался и не запускался как сервер. Зависимости Java
не загружались. Поэтому эти проверки измеряют статическое построение и
его ограничения. Они не измеряют работу кластера или качество RCA по его логам.

### Два дефекта Java frontend

**`yield` при JAVA_25.** Joern выбирает JAVA_25. Его JavaParser 3.28.0 не включает
этот уровень в `yieldSupport`. JDK 21 успешно компилирует минимальный пример,
но JavaParser создаёт `UnparsableStmt`. Отдельный JavaParser 3.28.2 проходит
тот же пример. Полный Joern с обновлённой зависимостью ещё не проверен.

**Lambda в enum.** Минимальный enum передаёт lambda в аргумент конструктора.
Joern вызывает `scope.enclosingMethod.get`, получает `None.get` и пропускает
файл. Exit code остаётся 0. Экспорт содержит 11 узлов, 8 рёбер и 0 METHOD,
хотя исходный файл содержит конструктор и метод `apply()`.

В полном запуске были 26 сообщений о parser problems, 26 предупреждений
`UnparsableStmt` и три явных пропуска файлов. Повторные сообщения не являются
числом разных пропущенных операторов. Диагностики записаны отдельно от exit code.

Примеры, команды и первичные ссылки:
[подробный отчёт OpenSearch](research/2026-11-22-opensearch.md).

## Нужно ли менять Joern

Сейчас обоснован следующий порядок: исправить слой обработки CPG, проверить
полноту frontend, затем сравнить способы хранения и извлечения данных.
Полученные задержки имеют конкретные причины. Они не доказывают необходимость
полной замены Joern.

GraphML был проверен на том же snapshots-графе. Экспорт занял 34,001 секунды
и 2 695,82 MiB RSS. Импорт NetworkX занял 12,374 секунды и 906,70 MiB.
После простого адаптера оставались различия в атрибутах 9 410 узлов.
Различались и атрибуты рёбер. Некоторые длинные строки получили переносы и
отступы. Поэтому совпадения числа узлов и рёбер недостаточно для замены формата.

Следующий полезный эксперимент — извлечение нужных методов из native CPG
через Joern API. Joern поддерживает [сервер запросов][joern-server] и
[несколько форматов экспорта][joern-export]. Такой эксперимент должен вернуть
те же CALL, CFG, DDG и связи вызовов, что и эталон. Только затем можно сравнить
время, память и размер артефактов.

Tree-sitter даёт [синтаксическое дерево][tree-sitter]. Для сопоставимого RCA
потребуются дополнительные разрешение символов, CFG, data flow и связи вызовов.
Он может быть полезен как лёгкий fallback для места лога. Это не готовая
равнозначная замена текущему CPG. CodeQL также требует отдельного сравнительного
эксперимента. Он здесь не запускался.

## Покрытие публичных runtime-логов

Использован публичный случай RCAEval `re3ob_adservice_f3_1` из revision
`afeacb11bcc94dadfd1c8f483ee4377b2b8b614e`. Всего 70 558 строк и 6 968 разных
пар «сервис, сообщение». CSV проверен по исходному Parquet: значения всех
ячеек совпадают. SHA-256 Parquet соответствует сохранённому manifest.

Каждое уникальное сообщение сопоставляется один раз. Его частота задаёт вклад
в число строк. Порядок событий и поиск цепочек в этой проверке не используются.

Baseline matcher взят из исходного master. Точное равенство reader и pydot

для перевода reader из эксперимента в основной режим.

Рост составляет 22,28 процентного пункта. Новых совпадений — 15 717,

улучшение диагностики.

873 случая. Online и offline вернули одинаковые наборы и включили исходный CALL.
Эти строки синтетические. Их нельзя объединять с runtime-покрытием.

## Что ограничивает качество модели

После исправлений все 10 bundled-сервисов строятся без ошибки. Найдено
254 точки входа, 291 log point, 135 reachable и 86 visible call sites.
220 точек входа не имеют видимого лога. Из 118 pooled-потерь 115 находятся
в вызываемых методах. Cartservice имеет 14 шаблонов и 0 точек входа.

В OpenSearch snapshots картина сходная: из 69 distinct reachable sites видны
46. Все 77 pooled-потерь находятся в callees. Текущий FSM описывает главным
образом entry method. FLOW может содержать метод, лог которого не попал в FSM.

Следующий шаг требует модели call/return. Простое добавление всех логов callee
в последовательность не сохраняет ветвления, несколько мест вызова, recursion,
exceptions и async. Нужны маленькие программы с известными реальными трассами
и проверкой допустимых путей.

Также остаются ошибки определения настоящих logger calls и извлечения сложных
шаблонов. Например, создание объекта ошибки не всегда является записью лога.
Для исправления нужен реестр logger API с учётом receiver и language frontend.

## Память online-истории

Лимит active hypotheses не ограничивает всю сохранённую историю. Проверка
с синтетическим loop оставляла ровно одну активную гипотезу и одну цепочку.

| События | Сохранённые гипотезы | Ссылки на логи | Peak Python allocation |
|---|---:|---:|---:|
| 100 | 100 | 5 050 | 205 864 байт |
| 500 | 500 | 125 250 | 3 377 128 байт |
| 1 000 | 1 000 | 500 500 | 12 754 192 байт |

Каждый дочерний путь копирует списки и кортежи родителя. Старые гипотезы остаются
в памяти. В этом примере число ссылок равно `N*(N+1)/2`. Это отдельная проблема
от хранения CPG. Память измерена через tracemalloc, а не RSS.

Предлагаемое решение — узлы истории с parent links и отдельная политика
retention. Разворачивать полный путь нужно по запросу. Старый исследовательский
прототип DAG полезен для эталонных проверок. Перенос требует сохранения
корреляции и полного множества допустимых путей на малых примерах.
Результат: [history-growth.json][history-results].

## Оценка качества и малая проверка агентов

Evaluator теперь сохраняет весь набор ground-truth случаев. Например,
при двух случаях и одном правильном ответе AC@1 и MRR равны 0,5.
Прежний код показывал 1,0, поскольку второй случай не участвовал в расчёте.
Наличие ответа и правильность ответа считаются отдельно.

Два новых агента получили один публичный инцидент. Родительский контекст
им не передавался. Каждый агент мог прочитать только свой пакет. Метка
сервиса и имя исходного файла в пакеты не попали. Это ограничение инструкции,
а не изоляция файловой системы.

В обоих пакетах одинаковы окна: 120 секунд до и 120 секунд после момента
инцидента. Сообщения выбраны одним алгоритмом для всех 10 сервисов. Числа,
UUID и email заменены до группировки. Второй пакет добавляет статические
кандидаты для тех же сообщений.

| Вход | Размер JSON-файла | Первый сервис | Ответ получен |
|---|---:|---|---|
| Сводка логов | 9 290 байт | adservice | Да |
| Та же сводка + кандидаты | 25 263 байта | adservice | Да |

Оба агента указали остановку или запуск adservice как гипотезу. Оба сохранили
неопределённость причины остановки JVM. Второй агент добавил методы `chooseAd`
и `start`. Ранжирование не изменилось. Проверка не показала роста точности
на этом случае. Размер JSON-файла вырос в 2,72 раза; без форматирования — в 2,84.
Количество токенов, стоимость и время ответа не измерялись.

Это один независимый инцидент с двумя вариантами входа. Из него нельзя получить
оценку улучшения RCA на проектах в целом. Для следующего исследования нужны
несколько проектов, разные типы сбоев, healthy controls, пропуски логов,
перемешанные запросы и случаи с несовпадающей версией кода.

Пакеты, ответы и ограничения: [agent-pilot](../eval/results/agent-pilot).

## Какой интерфейс нужен агенту

Полезно выдавать данные по конкретному запросу. Начальный ответ должен содержать
места логов, допустимые продолжения и явные пробелы. Полный CPG обычно избыточен.

Предлагаемый набор операций:

1. `resolve_log`: service, build ID, message → кандидаты CALL с причиной выбора.
2. `explain_window`: ограниченное окно и ключ корреляции → совместимые цепочки,
   необъяснённые события и причины остановки.
3. `get_slice`: выбранная гипотеза → методы, места логов и ссылки на исходный код.
4. `get_coverage`: пропуски frontend, unresolved calls, limits и версия артефактов.

Это план интерфейса, а не реализованный MCP API. Для такого интерфейса нужны
контракт данных и проверка provenance. У каждой модели должны быть source commit,
версия Joern, frontend options, logger rules и digest артефакта. У runtime-входа
нужен deployment/build ID, если он доступен.

## Предлагаемые задачи

| Приоритет | Задача | Критерий готовности |
|---|---|---|
| P0 | Дополнить #10 измерениями и отдельным local-edge fix. | Одинаковые inputs; stage time/RSS; точное равенство структур; минимум три независимых повтора в CI. |
| P0 | Проверять полноту Java frontend. | Оба Java repro видны в CPG или сборка явно сообщает partial. Exit code не является единственным критерием. |
| P0 | Влить исправления matcher, evidence и evaluator небольшими PR. | Regression tests проходят; optional correlation сохраняет ключи и не склеивает запросы. |
| P1 | Добавить call/return в модель логов. | Callee logs видны; тесты проверяют несколько call sites, branch, return, exception и recursion limits. |
| P1 | Ограничить online-историю. | Размер истории при длинном потоке измеряется отдельно от active beam; paths сохраняются через parent links; есть retention. |
| P1 | Уточнить entrypoints и logger registry. | C# handler fixture имеет точку входа; объекты ошибок не считаются логами без основания; неизвестные вызовы помечаются. |
| P1 | Зафиксировать source/runtime provenance. | Несовпадение build ID явно видно до диагностики. |

| P2 | Расширить слепую agent evaluation. | Фиксированы случаи, prompt, модель, бюджет и варианты входа; учитываются timeout, abstention и все неуспешные случаи. |

## Повторение проверок

Установить проверенный набор зависимостей и выполнить тесты:

```bash
python -m pip install -r eval/requirements-test.txt
PYTHONHASHSEED=0 python -m pytest -q
```

Построить bundled-сервисы и проверить контракт matcher:

```bash
PYTHONHASHSEED=0 python builder.py --dot-parser joern --output-dir output/check
python -m eval.check_matcher_parity output/check --output output/matcher.json
python -m eval.coverage output/check output/coverage
```

Измерить публичные логи после отдельного получения CSV:

```bash
python -m eval.runtime_match_coverage logs.csv output/check \
  --output output/runtime-matches.json --outcomes output/runtime-outcomes.json
```

Проверить рост истории:

```bash
python -m eval.profile_history_growth --output output/history-growth.json
```

Для OpenSearch использовать [инструкцию benchmark](opensearch-benchmark.md).
Workflow закрепляет source commit, Joern archive digest и версии Actions.
Тестовый workflow использует проверенные Python dependencies. Тяжёлый workflow
имеет лимит 60 минут, а отдельные команды — лимиты времени и sampled RSS.
Артефакты включают измерения и диагностики. Большие DOT/CPG и runtime-логи
не включены в загрузку Actions.

Первый запуск по умолчанию проверяет notifier через pydot, затем snapshots
через строгий reader. Ручной запуск должен использовать ветку, содержащую
reader. Подготовленная integration branch это условие выполняет.
