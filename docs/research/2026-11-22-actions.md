# Продолжение исследования: GitHub Actions, 22 ноября 2026 года

## Основной результат

Исправления и эксперименты опубликованы в `moleus/cpg_rca`.
Повторный эксперимент подтвердил ускорение построения FLOW/FSM в 29,2 раза.
Компактная история снизила пик выделений Python в 82,7 раза на цепочке из
5000 событий. Индекс гипотез сократил время store в 56,7 раза на 20 000
синтетических событиях. Проверка Java frontend выявила две разные причины потери кода.
Native CPG OpenSearch со штатными исключениями прошёл пять явных overlays:
получены 5,59 млн узлов и 40,37 млн рёбер при максимальном RSS 9,68 GiB.
Эти результаты имеют разные границы применимости; они описаны ниже.

Все приведённые сравнения выполнены на публичном коде или синтетических
событиях. Данные из личной переписки и закрытые runtime-логи в репозиторий не
добавлены. Основная ветка fork не изменена. Отчёт и проверенные исправления
находятся в [research/rca-validation-2026-11-22](https://github.com/moleus/cpg_rca/tree/research/rca-validation-2026-11-22).

## 1. Контролируемое сравнение OpenSearch

Вход — пакет `server/src/main/java/org/opensearch/snapshots` из OpenSearch
`2220907d3119897b8bd58cbc3c926787cd05ed2c`: 30 Java-файлов. Joern закреплён на
версии `4.0.689`; SHA256 архива проверяется до запуска. Для сравнения построен
один DOT: 45 756 узлов и 333 948 рёбер.

Оба варианта используют одинаковый строгий DOT reader. В baseline заменён
только `src/offline/method.py` на исходный файл upstream `f8bb418`. Другой
вариант читает исходящие рёбра узлов AST конкретного метода. Перед каждым
запуском проверяются входной файл и SHA исходного модуля. Проверяется и SHA
фактически загруженного модуля.

Каждый вариант получил три запуска в новом процессе. Порядок: AB, BA, AB.
Установлен `PYTHONHASHSEED=0`. Чтение SHA прогревает файловый кэш ОС. Эти
результаты не являются измерением холодного диска.

| Показатель | Полный обход рёбер | Обход рёбер метода | Отношение медиан |
|---|---:|---:|---:|
| FLOW/FSM, медиана | 65,189 с | 2,229 с | 29,2× |
| Весь Python-этап, медиана | 69,446 с | 6,415 с | 10,8× |
| Весь Python-этап, диапазон | 69,405–69,670 с | 6,315–6,649 с | — |
| Загрузка DOT, медиана | 3,133 с | 3,081 с | — |
| Пик RSS процесса, медиана | 342,72 MiB | 343,11 MiB | Почти без изменения |

Все шесть запусков построили 106 шаблонов и 89 entrypoints без ошибок.
Во всех случаях совпали **180 файлов**: все FLOW, FSM, trie и index.
Сравнение выполнено непосредственно по байтам, без сортировки массивов или
удаления полей. Также совпали показатели покрытия.

Источник: [Actions run 45022293329](https://github.com/moleus/cpg_rca/actions/runs/45022293329),
[полный JSON сравнения](../../eval/results/actions-2026-11-22/method-comparison.json).
Это результат одного runner и трёх повторов на вариант. Доверительный интервал
не рассчитывался. Он не задаёт ускорение всего OpenSearch или прежнего пути
с pydot: в этом сравнении reader одинаков.

**Решение.** Локальный обход рёбер можно готовить к отдельному review.
Для него есть [узкая ветка](https://github.com/moleus/cpg_rca/tree/fix/local-method-edge-scan).
Работу над форматом и загрузкой графа следует согласовать в рамках
[upstream #10](https://github.com/ch4t5ky/cpg_rca/issues/10), где исполнитель — Lileeid.

## 2. Проверка строгого DOT reader

В том же workflow выполнено точное сравнение pydot и строгого reader на трёх
малых реальных Java-исходниках. Проверены записи узлов, атрибуты, порядок рёбер,
ключи параллельных рёбер и созданные файлы.

| Исходный scope | Узлы | Рёбра | Entry points | Проверено выходных файлов |
|---|---:|---:|---:|---:|
| RestoreCompletionNotifier | 607 | 3027 | 1 | 4 |
| InternalSnapshotsInfoService | 2278 | 14 361 | 4 | 10 |
| RecoveryFailedException | 272 | 1331 | 0 | 2 |

Все сравнения прошли. Последний пример проверяет граф, trie и index; он не
проверяет непустой FLOW. Время и RSS этого job нельзя использовать для
сравнения затрат readers: он хранит оба графа в одном процессе и всегда
запускает pydot первым. Его цель — проверка равенства.

Источник: [reader-equivalence.json](../../eval/results/actions-2026-11-22/reader-equivalence.json).
Строгий reader по-прежнему включается явно. Он поддерживает ограниченный
формат Joern и возвращает ошибку для неподдерживаемого синтаксиса.

## 3. Можно ли хранить меньше рёбер

Отдельный эксперимент оставляет все узлы и их атрибуты, но сохраняет только
шесть меток рёбер, которые читает текущий offline-код: `AST`, `CFG`,
`CONDITION`, `CONTAINS`, `CDG`, `REACHING_DEF`.

Простое удаление остальных рёбер оказалось недостаточным. NetworkX задаёт
порядок соседей по первому ребру любой метки. Удаление раннего `ARGUMENT`
могло переставить последующие `AST`-рёбра и изменить шаблон лога. Добавлены
регрессионные примеры и восстановление порядка исходящих и входящих соседей.
Все входные строки DOT проверяются, включая отброшенные рёбра.

На исправленном варианте выполнены три пары запусков на одном snapshots DOT:

| Показатель | Полный граф | Проекция |
|---|---:|---:|
| Узлы | 45 756 | 45 756 |
| Рёбра | 333 948 | 194 725 |
| Пик RSS, медиана | 343,19 MiB | 308,38 MiB |
| Весь Python-этап, медиана | 5,593 с | 5,451 с |
| Проверено файлов за запуск | 180 | 180 |

Удалено 41,7% рёбер. Пик RSS снизился на 10,1%. Время изменилось примерно на
2,5%; это малый эффект в одном эксперименте. Все выходные файлы совпали.
Дополнительная проверка прошла на всех десяти встроенных сервисах:
**528 разных выходных файлов** совпали между вариантами. У cartservice
осталось ноль entrypoints; этот scope проверяет только его trie и index.

Источники: [Actions run 45022846907](https://github.com/moleus/cpg_rca/actions/runs/45022846907),
[snapshots](../../eval/results/actions-2026-11-22/edge-projection.json),
[десять сервисов](../../eval/results/actions-2026-11-22/bundled-projection.json).

**Решение.** Проекция остаётся в
[отдельной ветке](https://github.com/moleus/cpg_rca/tree/experiment/cpg-edge-projection).
Она привязана к текущим consumers и внутренним структурам NetworkX 3.6.1.
Это не полный CPG. Она не сохраняет исходные ключи параллельных рёбер и
не подходит для произвольного графового анализа. Основной выигрыш по времени
уже получен за счёт локального обхода. Для следующего существенного снижения
памяти стоит проверять компактный native export или загрузку отдельных
методов. DOT-текст, атрибуты всех узлов и NetworkX всё ещё занимают память.

## 4. История runtime: общий префикс вместо копий

В реальный `ExplicitHypothesisStore` добавлен экспериментальный параметр
`compact_history=True`. Каждый ребёнок хранит одно событие и ссылку на общий
префикс. При чтении строятся прежние `list` и `tuple`. Режим по умолчанию
выключен.

Проверены ветвление, повторное объединение, цикл, завершение, ограничения
гипотез, тайм-аут, неполный статический путь и корреляция запросов. Сравниваются
события, `asdict`, DataFrame, отчёты и итоговые гипотезы. Коллизия хеша dedup
имеет отдельный тест. Добавлены итеративный `deepcopy` и поддержка независимых
полей в `dataclasses.replace`.

Финальный Actions run использует commit `2c40d86`. Он прошёл 178 тестов и
50 дополнительных случаев. Все 32 измерительных процесса завершились.
Каждый размер получил по три замера времени и отдельный запуск tracemalloc
для каждого режима. Хеши входа и результата совпали.

| События | Python allocation: копии | Python allocation: общий префикс | Время обработки: копии | Время обработки: общий префикс |
|---:|---:|---:|---:|---:|
| 100 | 0,196 MiB | 0,076 MiB | 0,00165 с | 0,00156 с |
| 500 | 3,232 MiB | 0,344 MiB | 0,01818 с | 0,01586 с |
| 1000 | 12,190 MiB | 0,700 MiB | 0,06276 с | 0,05261 с |
| 5000 | 289,808 MiB | 3,505 MiB | 1,44127 с | 1,08041 с |

На 5000 событиях пик выделений Python снизился в 82,7 раза. Число сохранённых
ссылок на логи изменилось с 12 502 500 до 5000. Наибольший пик RSS среди трёх
запусков без tracemalloc снизился с 380,23 до 93,51 MiB. Он включает импорты и отличается
от показателя tracemalloc. Время в таблице — медиана обработки store без
tracemalloc; выгрузка полного результата в него не входит.

Источник: [Actions run 45023212719](https://github.com/moleus/cpg_rca/actions/runs/45023212719),
[compact-history.json](../../eval/results/actions-2026-11-22/compact-history.json).
Первый run на предыдущем commit тоже сохранён в архиве. Его время нельзя
смешивать с финальным запуском на другом runner.

**Ограничения.** Это синтетический цикл с одной активной гипотезой, а не
реальная частота обработки логов сервиса. Все 5000 старых гипотез ещё хранятся.
Без отдельного индекса поиск активных гипотез имеет квадратичную стоимость. Выгрузка
всех полных префиксов создаёт квадратичный объём данных. Изменение полученного
списка `logs` меняет только снимок. Индекс проверен отдельно ниже; явная
политика хранения остаётся следующей задачей. [Ветка и договор API](https://github.com/moleus/cpg_rca/tree/experiment/compact-runtime-history).

### 4.1. Индекс активных и завершённых гипотез

Следующий опыт устранил повторные проходы по старым гипотезам. Новый параметр
`index_hypotheses=True` поддерживает индексы `active` и `completed`. Порядок
остаётся прежним. Оба сравниваемых варианта уже используют компактную историю.
В каждом размере выполнены три замера времени и один отдельный замер памяти.

| События | Сканирование, медиана | Индекс, медиана | Отношение медиан |
|---:|---:|---:|---:|
| 100 | 0,00377 с | 0,00300 с | 1,26× |
| 1000 | 0,10354 с | 0,02830 с | 3,66× |
| 5000 | 2,09233 с | 0,13852 с | 15,1× |
| 20 000 | 30,98308 с | 0,54675 с | 56,7× |

Все 32 процесса завершились. Хеши входа и результата совпали. Для 20 000
событий диапазоны времени: 30,861–33,784 с и 0,546–0,555 с. Python allocation
изменился с 14 741 368 до 14 742 168 байт: индекс добавил 800 байт на этот
вход с одной цепочкой. Сохранены все 20 000 гипотез. Измерены создание store
и `process()` с известным CALL ID. Сопоставление через trie и экспорт
полного результата в это время не входят.

Actions прошёл 203 теста и 50 дополнительных случаев. Отдельная локальная
проверка против исходных модулей предыдущей ревизии сохранила точные JSON,
обе DataFrame и итоговые отчёты в 16 случаях с 84 событиями.

Режим включается явно. Он работает, пока store владеет изменяемыми гипотезами.
Чтение публичного словаря или непустого списка живых гипотез постоянно
возвращает эту цепочку к прежнему сканированию. Это сохраняет прямые изменения
словаря и статусов, aliases, copy и `dataclasses.replace`. Внутренние отчёты
возвращают значения и сохраняют индекс включённым.

Источники: [Actions run 45025027002](https://github.com/moleus/cpg_rca/actions/runs/45025027002),
[active-index.json](../../eval/results/actions-2026-11-22/active-index.json),
[проверка прежней ревизии](https://github.com/moleus/cpg_rca/blob/experiment/active-hypothesis-index/eval/results/active-index/previous-revision-equality.json),
[договор API](https://github.com/moleus/cpg_rca/blob/experiment/active-hypothesis-index/docs/active-hypothesis-index.md).
Это синтетический цикл. Индекс не ограничивает историю и не устраняет обход
сохранённых цепочек, расчёт score и повторное чтение растущего списка completed.

## 5. JavaParser не устраняет все потери Java-кода

Сравнены две изолированные конфигурации Joern 4.0.689: штатные JavaParser core
и symbol-solver 3.28.0 и согласованная пара 3.28.2. Проверяется фактический
classpath. Исходный дистрибутив не изменяется. Вход — два минимальных примера
и восемь заранее выбранных файлов OpenSearch с известными проблемами.

| Наблюдение на восьми файлах OpenSearch | 3.28.0 | 3.28.2 |
|---|---:|---:|
| Строки сообщений об ошибках синтаксиса | 10 | 0 |
| Файлы с `Failed to process` | 2 | 2 |
| Внутренние METHOD | 258 | 258 |
| CALL | 2510 | 2548 |
| Кандидаты log CALL по имени | 15 | 15 |
| UNKNOWN | 7 | 13 |

Замена библиотек убирает найденную ошибку разбора `yield`. Но в Joern
[нет обработки YieldStmt](https://github.com/joernio/joern/blob/v4.0.689/joern-cli/frontends/javasrc2cpg/src/main/scala/io/joern/javasrc2cpg/astcreation/statements/AstForStatementsCreator.scala#L51-L78).
Он создаёт `UNKNOWN`, не строя выражение внутри yield. Минимальный пример
с `yield bits ^ 1L` даёт ноль CALL в обоих source-вариантах.

У lambda в enum другая ошибка. Параметры регистрируются через
[`scope.enclosingMethod.get`](https://github.com/joernio/joern/blob/v4.0.689/joern-cli/frontends/javasrc2cpg/src/main/scala/io/joern/javasrc2cpg/astcreation/expressions/AstForLambdasCreator.scala#L479-L483)
до создания области lambda. Минимальный файл даёт 11 узлов, 8 рёбер и ноль
внутренних методов, хотя команда завершается с кодом 0. Ошибка сохраняется
после замены JavaParser. Кандидат исправления и необходимые проверки
владения параметрами описаны в backlog; патч Joern не применялся.

Источники: [Actions run 45022463665](https://github.com/moleus/cpg_rca/actions/runs/45022463665),
[полное сравнение](../../eval/results/actions-2026-11-22/java-source-comparison.json).
Это набор известных сбоев, а не случайная выборка для оценки покрытия Java.
Зависимости OpenSearch не загружались. Число узлов или CALL не доказывает
правильность CFG и data flow. Успешный workflow означает завершение измерений,
а не полноту полученного CPG.

## 6. Проверка bytecode frontend

Те же два примера скомпилированы JDK 21.0.13. `javap` независимо подтверждает

создаёт дополнительные методы.

Источники: [Actions run 45023047806](https://github.com/moleus/cpg_rca/actions/runs/45023047806),

## 7. Полный OpenSearch: отдельная проверка применимости

Завершён [Actions run 45024003121](https://github.com/moleus/cpg_rca/actions/runs/45024003121).
Frontend получил все 13 770 отслеживаемых Java-файлов: 124 664 521 байт
исходников. Но [штатный фильтр Joern](https://github.com/joernio/joern/blob/v4.0.689/joern-cli/frontends/x2cpg/src/main/scala/io/joern/x2cpg/frontendspecific/javasrc2cpg/package.scala)
исключает 4657 файлов с компонентом пути `test`. Среди них 353 файла внутри
`src/main/java`. После фильтра остаётся 9113 файлов. Это запуск на входе всего
репозитория со штатными исключениями, а не доказательство разбора каждого
входного файла.

| Native Java parse, sampled process-tree RSS | 9,06 GiB |

| Подсчёт внутри query | 3,944 с |

Frontend завершился с кодом 0. При этом журнал содержит три `Failed to process`,
26 сообщений о проблеме синтаксиса и 26 сообщений о неразобранном операторе.
Три аварийных файла: `HashFunctionBenchmark.java`,
`DerivedFieldSupportedTypes.java` и `ResourceType.java`. Полнота source CPG
остаётся `not_established`. FILE node может появиться до ошибки построения AST.
Число FILE nodes поэтому также не доказывает успешный разбор тела файла.

Отдельный read-only запрос к сохранённому CPG подтвердил точное равенство
9113 FILE names и допустимых путей manifest. Три аварийных пути имеют FILE,
но не имеют NAMESPACE_BLOCK и METHOD. У 793 допустимых файлов нет METHOD:
754 — `package-info.java`, 36 — интерфейсы без собственных методов, три —
аварийные файлы. Это объясняет счётчики файлов; правильность всех языковых
конструкций такая проверка не устанавливает.
[Проверка scope](../../eval/results/actions-2026-11-22/opensearch-source-scope-audit.json)
сохраняет хеши входов и множеств путей. Query выполнен локально с фактически
проверенными 3 GiB heap и двумя CPU; исходный CPG не изменился.

В графе нет overlays; число рёбер CFG, CALL и REACHING_DEF равно нулю.
CALL nodes при этом присутствуют. Query не изменил файл: SHA256 до и после
совпал. Большой DOT, NetworkX и FLOW/FSM в этом запуске не использовались.

Для frontend заданы heap 8 GiB и `ActiveProcessorCount=4`. Монитор ограничивает
суммарный RSS группы процессов до 12 GiB и время parse до 1200 секунд.
Query имеет отдельный предел 300 секунд. Поздний smoke выявил, что `-J` flags
не передаются автоматически в дочернюю JVM Scala script. Поэтому heap query
в этом run не считается проверенным лимитом 8 GiB. Фактический sampled RSS и
время в таблице измерены; предел process-tree RSS действует независимо от heap.
Новые script-замеры должны использовать `JDK_JAVA_OPTIONS` и проверку Runtime.

На одном notifier проверена явная цепочка
`base → controlflow → typerel → callgraph → dataflowOss`. Только после неё
получены все нужные виды рёбер. Попытка dataflow после одного controlflow
завершилась ошибкой обязательного REF у METHOD_REF. Слои нельзя удалять только
на основании пустого списка зависимостей в `OssDataFlow`.
Это отдельный малый опыт с одним запуском каждой стадии, не измерение всего
OpenSearch. [Сырые результаты](../../eval/results/actions-2026-11-22/local-notifier-overlay-stages.json)
и [проверка child JVM](../../eval/results/actions-2026-11-22/local-script-jvm-limits.json)
сохранены отдельно от Actions-замеров.

Источник: [измеренный summary](../../eval/results/actions-2026-11-22/opensearch-full-native-summary.json).
Длинный список METHOD filenames сохранён в сыром архиве. Настройки и результаты
прежнего локального тайм-аута отличаются. Отношение времени этих двух запусков
нельзя представлять как ускорение кода.

### 7.1. Все пять overlays на большом сохранённом графе

[Actions run 45025461098](https://github.com/moleus/cpg_rca/actions/runs/45025461098)
получил точный gzip из первого run. SHA256 gzip и raw CPG проверены до работы.
Повторный parse не выполнялся. Все пять стадий завершились в пределах одного
общего бюджета 1200 секунд. В каждой дочерней JVM подтверждены heap 8 GiB и
четыре доступных процессора; affinity также ограничена четырьмя CPU.

| Стадия | Весь процесс | Применение слоя внутри JVM | Sampled peak RSS |
|---|---:|---:|---:|
| base | 25,780 с | 5,649 с | 6,79 GiB |
| controlflow | 29,160 с | 8,269 с | 8,01 GiB |
| typerel | 25,133 с | 1,059 с | 6,33 GiB |
| callgraph | 28,650 с | 5,851 с | 6,56 GiB |
| dataflowOss | 51,321 с | 26,371 с | 9,68 GiB |

Общая обработка с восстановлением входа и проверками заняла **161,531 с**.
Сумма CPU user + system пяти процессов — 401,611 с. Сумма времени самого
применения слоёв — 47,199 с. Остальное включает запуск JVM, компиляцию script,
загрузку, подсчёт рёбер, сохранение и служебные проверки. Нельзя приписывать
всё это время одному проходу data flow.

Итоговый native CPG имеет **5 585 584 узла, 40 374 361 ребро** и размер
188 046 089 байт. В нём есть 3 431 902 CFG, 1 283 209 CDG, 1 678 171 CALL
и 9 240 004 REACHING_DEF рёбер. Число UNKNOWN осталось 26. Исходный raw CPG
не изменился. При переходе между стадиями проверены повторно загруженные
счётчики и ожидаемый список overlays.

Это один запуск на каждом слое. Полнота source и data flow не установлена.
Использован [штатный предел 4000 definitions на метод](https://github.com/joernio/joern/blob/v4.0.689/dataflowengineoss/src/main/scala/io/joern/dataflowengineoss/passes/reachingdef/ReachingDefPass.scala).
Полнота data flow каждого метода отдельно не проверялась. DOT, NetworkX,
извлечение шаблонов и FLOW/FSM на этом большом графе ещё не запускались.

Источник: [полный JSON стадий](../../eval/results/actions-2026-11-22/opensearch-full-overlays.json).
Полученный результат обосновывает следующий опыт с native export каталога.
Он не даёт оснований считать Joern неприменимым только из-за размера графа.

## 8. Что это меняет в архитектуре

[Подробный проект архитектуры](2026-11-22-architecture.md) описывает границы
этапов, API для агента, альтернативные инструменты и следующую оценку.

Первый необходимый шаг — отделить полноту исходного графа от скорости его
обработки. Manifest должен хранить commit исходников, frontend, параметры,
диагностику, overlays и хеш CPG. Команда с exit code 0 может потерять целый
файл; это уже воспроизведено.

В offline-части имеет смысл строить граф метода один раз и сохранять общий
каталог методов, шаблонов и мест вызова. Полный CPG нужен при подготовке.
Агенту обычно нужен малый набор кандидатов около выбранных логов. Новый
компактный формат должен иметь явный набор полей и проверку равенства с
действующим построителем. Смена DOT на другой текстовый формат сама по себе
не решает стоимость NetworkX.

Следующий пробел — вызываемые методы. В snapshots достижимы 69 уникальных
точек логирования; FSM показывает 46 и теряет 23. При отдельном учёте каждой
пары `(entrypoint, log CALL)` получаются 123 достижимые пары, 46 видимых и 77
потерянных. Все 77 потерянных пар относятся к callees. Это не число runtime-строк.
Текущая FSM строится только по графу входного метода. Для исправления нужна
модель вызова и возврата с правильной точкой продолжения, а также явные
пределы рекурсии, исключений и асинхронных вызовов.

В online-части общий префикс снимает одну причину роста памяти. Опциональный
индекс снимает повторные обходы старых гипотез в проверенном scope. Для долгой
работы требуется ограниченное хранение завершённых состояний.
События следует связывать по явному ключу внутри сервиса.
Совпадение шаблона даёт кандидата в исходном коде. Для вывода о причине сбоя
нужны дополнительные доказательства связи событий.

Ответ инструмента для агента должен содержать matched и unmatched события,
кандидаты CALL ID, версию исходников, границы статического анализа и причины
неполной цепочки. Статическое условие обозначает возможную ветку. Оно не
доказывает, какое значение имело условие во время инцидента.

Драйверы, зависимости, workflows и исходные параметры находятся в этих
ветках. Workflow запускается при изменении предусмотренных файлов своей
ветки. Все Actions закреплены по SHA; задания имеют предел времени и памяти.
Результаты доступны в JSON рядом с этим отчётом.
[Указатель доказательств](../../eval/results/actions-2026-11-22/README.md) и
[provenance](../../eval/results/actions-2026-11-22/provenance.json) связывают
ветки, точные деревья git, 11 завершённых runs и 16 проверенных Actions artifacts.
Два небольших архива сохраняют сырые измерения, логи, выходные файлы и четыре
контрольных DOT-входа. Большой native CPG хранится отдельно в Actions artifact
с указанным сроком хранения.

Новая серия не измеряет точность поиска root cause на наборе инцидентов.
Прежний agent pilot имеет один независимый случай. Для следующей оценки
нужны несколько инцидентов с проверенной версией исходников, скрытые ответы,
одинаковый бюджет входа и учёт незавершённых запусков. Повторные запуски одного
случая не увеличивают число независимых инцидентов.
